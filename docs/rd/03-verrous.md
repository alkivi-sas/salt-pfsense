# Verrous techniques

Statuts possibles : `ouvert`, `en cours`, `levé`, `levé partiellement`, `non levé`. Chaque changement de statut renvoie vers la ou les fiches d'expérience.

| # | Verrou | Hypothèse | Protocole | Critère de levée | Statut |
|---|---|---|---|---|---|
| V1 | **Identifiants volatils.** pfrest identifie un objet par son index dans `config.xml`, qui change à chaque suppression ou insertion. Un moteur déclaratif exige au contraire une identité stable. | Une clé métier par type d'objet et un cycle « relire → résoudre → écrire → revérifier » suffisent. | Suppressions et insertions intercalées, écritures concurrentes pendant un run (EXP-01). | 0 écriture sur le mauvais objet sur 1 000 itérations aléatoires. | ouvert |
| V2 | **Concurrence sur `config.xml`.** Le verrou de pfrest protège une requête, pas une séquence lecture → écriture. L'interface web, la synchronisation HA et d'autres runs peuvent s'intercaler. | Un verrou côté agent et une détection de conflit par l'historique de configuration suffisent. | Runs parallèles et modifications simultanées par l'interface web (EXP-02). | Tout conflit est détecté et le run échoue proprement, jamais d'écrasement silencieux. | ouvert |
| V3 | **Écriture et application séparées.** L'application est différée par défaut, sauf pour certains modèles appliqués d'office. Un modèle sans sous-système peut être déclaré « appliqué » à tort. | Une application regroupée par domaine, déclenchée sur changement, réduit le nombre de rechargements sans perte de cohérence. | Mesure du nombre de rechargements pf et de la durée de run, avant et après (EXP-03). | Au plus 1 rechargement par domaine et par run ; état appliqué vérifié dans pf. | ouvert |
| V4 | **Couverture incomplète.** Plusieurs fonctions n'ont pas d'endpoint, et les endpoints ajoutés localement sont effacés à chaque mise à jour du paquet. | Un helper générique sur liste blanche de chemins est plus durable qu'un endpoint ajouté. | Prototype des deux options, cycles de mise à jour du paquet (EXP-04). | L'option retenue survit à 3 cycles de mise à jour sans intervention. | ouvert |
| V5 | **Équivalence sémantique.** pfrest injecte des valeurs par défaut et change certains formats (listes, chaînes, base64, mots de passe en clair hachés côté serveur). | Un diff normalisé de `config.xml`, avec une liste d'exclusions explicite, suffit comme oracle. | Rejeu de chaque scénario sur les deux implémentations (EXP-05). | 0 écart hors registre. | ouvert |
| V6 | **Hétérogénéité des versions.** Une version pfrest ne couvre que quelques branches de pfSense, et l'API change entre versions mineures. | Une version épinglée par branche et une couche d'adaptation limitée aux champs qui changent suffisent. | Tests de contrat sur le schéma OpenAPI de chaque version épinglée (EXP-06). | Suite verte sur chaque version de la matrice. | ouvert |
| V7 | **Amorçage sans secret humain.** La première clé API exige normalement une authentification avec un compte administrateur. | La clé peut être générée par l'outil de gestion, et seul son hash est écrit localement, sans manipuler de mot de passe administrateur. | Amorçage sur équipement vierge, contrôle de l'authentification et des privilèges (EXP-07). | Amorçage idempotent ; clé jamais présente dans les journaux. | ouvert |
| V8 | **Traduction ISC → Kea.** Les modèles d'options et les encodages diffèrent entre les deux serveurs, et le failover n'a pas d'équivalent direct. | Une table de traduction fermée, qui refuse explicitement tout le reste, donne un service identique vu du client. | Captures DHCP avant et après migration, comparées option par option (EXP-08). | Offres identiques sur 100 % des scénarios ; 0 migration silencieuse d'une configuration non gérée. | ouvert |
